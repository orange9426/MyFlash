# 按角色和模式配置任务

## 编辑位置

| 角色 / 模式 | 文件 |
| --- | --- |
| 男角色 · 普通 | `src/lib/game/tasks/maleNormal.ts` |
| 男角色 · 地狱 | `src/lib/game/tasks/maleHell.ts` |
| 女角色 · 普通 | `src/lib/game/tasks/femaleNormal.ts` |
| 女角色 · 地狱 | `src/lib/game/tasks/femaleHell.ts` |

四份文件互相独立。目前普通和地狱模式分别复制了该角色的原有任务，尚未调整内容难度。修改其中一份不会影响其他文件。

`tasks/index.ts` 负责角色与模式的映射；`tasks/schema.ts` 只定义两个任务数组的类型，直接填写任务对象即可。`constants.ts` 不再保存男角色任务正文，`tasksFemale.ts` 目前主要保存女角色结局。旧的 `tasks` / `tasksFemale` 导出仅兼容普通模式，业务代码应通过 `getTasks(persona, mode)` 读取。

## 任务组与六层路线

| 键 | 使用位置 | 配置建议 |
| --- | --- | --- |
| `楼层任务` | 六层统一抽取，每层两个候选；普通模式零分结算也从这里补抽 | 建议至少 12 项 |
| `上楼任务` | 1→2→3→4→5→6，共抽 5 个 | 每项只上 1 层，建议至少 6 个 |

楼层是相对起始层的编号。例如起始层为 10 时，实际路线为 10–15 层，每一层从对应角色和模式的“楼层任务”中抽取。

“楼层任务”至少配置两个不同 ID，建议至少 12 项，以支持整局六层候选去重。“上楼任务”必须非空，建议至少 6 项。不要删除这两个字段。

原来未使用的 H 任务保存在 `docs/archived-extra-tasks.json`，不参与构建和抽取。需要启用其中某项时，可手动复制进相应模式的任务数组。

同一层的两个候选不重复；跨层优先使用本局未安排的任务，池子不足时允许跨层重复。若合并池只有一个任务，页面会明确显示只有一个可选项。两张卡分别提供“刷新”和“确认”：刷新仅替换指定候选，另一项保持原样，新候选也不会与它重复。两张卡共用每局两次免费刷新额度，从同一角色和模式的合并池选取；确认后不能再刷新。

候选卡展示已适配的正文、装备动作和预计积分。选定后只需完成该任务，另一候选不计分、不增加进度。刷新保留候选和选择结果。全程仍为六个已处理的楼层任务与五次上楼，共 11 个进度步骤。

准备页面的携带清单会考虑两项候选的需求，实际任务只需二选一；这里是所有候选的准备范围，不表示两项都要执行。

## 一项任务怎么写

每项任务现在是一个对象，原始正文和需求直接放在一起。向相应数组添加：

```ts
{
  id: "MN_A01",
  name: "出发检查",
  description: "穿好鞋袜，检查鞋带，准备前往下一层。",
  baseScore: 2,
  needs: {
    requireAll: ["鞋子", "短袜"],
    wear: { 短袜: "on", 鞋子: "on" },
    photo: false,
  },
},
```

| 字段 | 规则 |
| --- | --- |
| `id` | 非空、稳定的唯一标识；同一配置文件所有任务组之间不得重复 |
| `name` | 中文标题 |
| `description` | 中文任务正文；只是文字，不会自动产生计时器、输入框或答案判定 |
| `baseScore` | 建议使用非负整数，表示楼层任务的基础积分 |
| `needs` | 本任务的需求对象，见下表；无需在其他文件配置同名 ID |
| `urineBonus` | 原有可选规则字段，同时影响额外积分和事件计数；一般新任务省略 |

建议新增 ID 使用前缀：`MN_` 男普通、`MH_` 男地狱、`FN_` 女普通、`FH_` 女地狱。例如 `MN_A01`、`MN_B01`、`MN_C01`、`MN_U01`。本次复制保留了原有 ID，以保持现有规则；新任务不要复用不相关旧任务的 ID。

楼层任务实际得分还会叠加装备和模式加成。**当前上楼确认不发放 `baseScore` 积分**，修改上楼任务的分数字段不会自动给上楼加分。上楼的目标层由流程自动设置，不需要在配置里写 `targetFloor`。

## 装备要求与特殊文本

旧的 `TASK_NEEDS` 表已经移除。四份任务配置均已将原本生效的需求迁入各自的 `needs`，不再按 ID 查装备规则。模式之间即使 ID 相同，也可以配置不同需求；仍建议新增任务采用不同前缀，方便排查和去重。

| `needs` 字段 | 类型和默认值 | 作用 |
| --- | --- | --- |
| `requireAll` | 装备数组，默认 `[]` | 必须拥有全部列出的装备；参与抽取筛选及携带清单 |
| `requireAny` | 装备数组的数组，默认 `[]` | 每个组至少拥有一件，例如 `[["上衣", "长裤"]]` |
| `recommend` | 装备数组，默认 `[]` | 建议携带，影响抽取偏好和清单 |
| `wear` | 装备到状态的映射，默认 `{}` | 生成穿戴动作和预览 |
| `fullyBare` | 布尔值，默认 `false` | 整体脱除状态，包含鞋子；明确的单件 `wear` 配置优先 |
| `lowerBare` | 布尔值，默认 `false` | 只调整长裤、内裤，不自动改变鞋子和短袜 |
| `kneeling` | 布尔值，默认 `false` | 保留动作分类，当前无独立显示效果；字段名不是 `kneel` |
| `photo` / `sound` | 布尔值，默认 `false` | 生成附加说明，当前页面尚未显示 `extras` / `notes`；不启动相机、录音或计时器 |
| `urine` | 布尔值，默认 `false` | 保留分类标记；积分和事件计数仍由任务的 `urineBonus` 决定 |

`wear` 可用装备键：`上衣`、`长裤`、`内裤`、`短袜`、`鞋子`。常用状态是 `on`（穿上）、`off`（脱下）。其余旧状态 `mouth`、`neck`、`wrap`、`rolled` 的处理逻辑保持不变；`rolled` 用于上衣。

新增 `faded` 仅适用于长裤、内裤：已穿着时显示“褪到膝盖”，未穿时保留“未穿可跳过”的 `keep` 提示，通常不显示动作标签。人物预览保留当前穿着，不绘制位置变化，也不会自动修改实际装备或积分。

```ts
needs: {
  wear: { 长裤: "faded", 内裤: "faded" },
},
```

显式 `faded` 优先于整体穿戴状态。将它配置给其他装备会产生 TypeScript 错误；运行时对未经类型检查的数据也会忽略无效项。若希望未穿时安静跳过，不要另外将该装备配置为必需拥有。

**需求优先级：**

1. 写了 `needs`：采用该对象，其余字段补默认值，不再根据正文补推断。
2. `needs: {}`：明确没有装备或动作要求，不因原文含关键词自动添加。
3. 完全省略 `needs`：兼容从标题和正文关键词推断；新增任务建议显式填写。
4. `urineBonus > 0` 仍将对应分类标记设为 true，保留原有行为。

**鞋子规则：**

- `fullyBare: true` 包含鞋子；若显式写 `wear: { 鞋子: "on" }`，单件要求覆盖整体状态。
- `lowerBare: true` 不改变鞋子。
- 穿着鞋子、且需要穿上未穿的短袜，或脱下/取用当前脚上的短袜时，自动建议先脱鞋；已在包里的短袜不触发此建议。
- 明确写了 `wear.鞋子` 时，以上短袜自动建议不覆盖它。`wear` 表达目标状态，不是多步骤动作脚本。
- 提示、人物预览共用这套规则，不会自动修改存档中的实际穿着。鞋子的积分加成和随机移除保持原样。

正文仍经过 `advisor.ts` 中的 `concretizeDescription()`（随机选项及少量旧 ID 特例）和 `resolveTaskDescription()`（当前状态适配）。本次没有重写这些规则。不要把新任务复用为旧特殊 ID，例如 `U12`；需求虽已独立，正文特例仍可能触发。

任务正文不会因为 `needs` 自动重写。配置要求穿鞋时，请让正文也表达相同要求。重复 ID、空任务池和文案与需求矛盾仍需人工检查。

装备定义及商店价格仍在 `constants.ts`，并不随任务文件自动变化。

## 抽取与更新规则

开局进入商店前会预抽整局任务。楼层候选、刷新和普通模式零分结算补抽使用“楼层任务”；上楼抽取使用“上楼任务”。均读取当前角色、当前模式的配置。

修改配置后应重新开局。刷新同版本页面会恢复已预抽的存档，未必显示新文案。若要让发布后的用户也统一新开局，需要同步更新 `constants.ts` 初始状态和 `store.ts` 存档版本判断中的 `routeVersion`。

每次配置完执行：

```powershell
npm run lint
npm run build
```

然后分别新开普通、地狱模式，检查楼层任务、单层上楼和免费换任务。编译检查不能替代空池、重复 ID 和实际装备提示的检查。

本次没有调整结局：男角色结局仍在 `constants.ts` 的 `endingsNormal` / `endingsHell`，女角色结局在 `tasksFemale.ts`。如需整体调整模式风格，需另行编辑结局。

## 可视化任务编辑器（第一版）

首页“管理自定义任务”或顶部菜单“任务编辑器”可打开编辑器。自定义任务按任务包保存，每包指定角色、难度和楼层/上楼类型。同一角色与难度下的多个包会合并使用。

- 支持任务包与任务的新建、编辑、复制、删除。编辑完成后点击“保存任务包”。删除包立即保存，删除包内任务在保存任务包后生效。
- 内置任务只读，支持单项或整包“复制后编辑”。复制会重新生成 ID，并保留原任务需求。
- 开局仅支持“仅内置”或“仅自定义”。仅自定义至少需要匹配角色、难度的两个楼层任务和一个上楼任务，不自动补入内置任务。任务较少时跨楼层可以重复，同一层的两个候选不同。
- 自定义任务使用独立 localStorage 键 `myflashCustomPacksV1`。重新开局、清除当前进度不会删除；浏览器的清除站点数据仍会删除，应通过“导出”备份。
- 导入接受编辑器导出的 `myflash-task-pack` v1 JSON。预览展示数量、角色、难度、类型及校验错误；错误未修复时不能保存。确认后作为新副本加入，不覆盖已有包。
- 每包 1–200 个任务，文件最大 2 MB；本地最多 30 个包、1000 个任务。标题最多 80 字，正文最多 4000 字，基础分为 0–100 的整数。
- 开局将完整任务池保存为 `GameState.runTaskPools` 快照；预抽计划、候选替换、楼层/上楼补抽及零分结算都使用当局快照。编辑结果下一局生效。旧局无快照时沿用内置任务池，同时保留已保存的预抽计划。
- 若开局快照无法保存，界面会报错并阻止进入新局。任务包保存失败也会保留编辑内容，允许重试。

回归检查：`node scripts/check-task-editor.mjs`。覆盖导入预览不写入、错误定位、ID 重建、角色/难度/来源隔离、快照与刷新、任务替换、结算、重新开局和清除进度保留任务包。

## 随机变量

任务编辑器中可添加文本变量或装备变量。点击添加时会在正文末尾插入 `{{变量名}}`；也可以将标记移动到标题或正文的任意位置。同名标记在一次任务中使用相同结果。变量名可使用中文、字母、数字及下划线，但不能以数字开头。

- 文本变量：每行填写一个备选词，抽取时随机选择一个。备选词不能嵌套变量。
- 装备变量：勾选备选装备，并选择“当前穿着”“拥有”或“拥有但未穿着”。从符合范围的备选装备中抽一件。
- 可为装备变量设置穿上、脱下、卷起等状态。卷起仅支持上衣，褪到膝盖仅支持长裤或内裤。选中装备和状态会写入该次任务的 `needs.wear`，生成穿戴提示与人物预览。没有指定状态时只替换文本。
- 一个任务最多 10 个变量，每个文本变量最多 50 个备选词，每词最多 200 字。未定义、重名、未使用的变量及无效装备状态会在保存/导入预览时提示。
- 多个装备变量都必须有可行的选择；同一装备的互相矛盾的状态不能同时选中。如果没有可行组合，该任务不会进入候选。
- 装备状态只影响现有操作提示和人物预览，不新增临时脱装备的计分规则。

示例（任务对象）：

```json
{
  "id": "custom-example",
  "name": "检查{{装备}}",
  "description": "穿上{{装备}}，记录一个{{颜色}}物品。",
  "baseScore": 2,
  "needs": {},
  "variables": [
    { "key": "装备", "type": "equipment", "options": ["上衣", "长裤"], "source": "unworn", "wear": "on" },
    { "key": "颜色", "type": "text", "options": ["红色", "蓝色", "绿色"] }
  ]
}
```

抽取时机：当楼层/上楼任务池包含变量时，该类任务延后至实际到达对应步骤时，从当局任务池快照筛选、抽取并解析。没有变量的任务池继续沿用预抽计划。已显示的候选、已选任务及上楼任务将具体文本、需求和 `resolvedVariables` 一起保存，刷新和选定不会重抽。换任务使用当前装备重新筛选并解析新任务。任务包导出/导入只保留模板变量，不保留当局解析结果。

可用楼层任务不足两项时显示单个候选；没有可用任务时明确提示，允许无奖励跳过本步，或在恢复装备后点击“重新检查装备”。零分结算的追加抽取也会排除无可选装备的任务，没有符合条件的任务时不追加。

编辑器的“模拟装备并预览抽取”支持设置拥有和穿着状态，重复预览具体文本与操作提示，不改动当前局。

变量回归检查：`node scripts/check-task-editor.mjs scripts/task-variables-check.ts`。
